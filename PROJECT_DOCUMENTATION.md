# Plant Stock Manager — Project Documentation

ASP.NET Core 8 Razor Pages nursery ERP for Precision Agritech Pvt. Ltd. No EF Core: raw `Microsoft.Data.SqlClient` via `Data/DatabaseHelper.cs`, one repository class per feature, registered Scoped in `Program.cs`. Cookie authentication against the existing `dbo.IMSUsers`/`Designation` tables (BCrypt password hashes) — no ASP.NET Identity anywhere in the request pipeline.

## 1. Governing decisions

These were confirmed with the business owner before implementation and apply across every phase below.

**Decision 1 — Stock ledgers.** Every stock-bearing entity gets its own dedicated transaction table (`Id, TransactionDate, TransactionType, ReferenceType, ReferenceId, Quantity, BeforeQuantity, [AfterQuantity computed], UserId, Remarks, CreatedAt`) — never a single polymorphic `StockLedger` with `EntityType`/`EntityId`. In use: `SeedCuttingTx` (pre-existing), `InventoryTransactions` (pre-existing), `EmptyPotInventoryTransactions` (Phase 7), `PottedPlantStockTransactions` (Phase 7, reused by Phases 8–10 and 12 with additional `TransactionType` values rather than new tables).

**Decision 2 — `dbo.VendorPurchases` left alone.** Not read, altered, renamed, migrated, or reinterpreted anywhere in this project. Phase 11 built a clean, separate `PurchaseOrder`/`PurchaseReceipt` system instead.

**Decision 3 — Mother Plant patch.** `dbo.MotherPlants` uses `MotherPlantCode` (not `BatchNumber`) as its business identifier, plus `SupervisorId → IMSUsers.Id`. Completed in Phase 2, before Phase 3 began.

Two further decisions came up mid-project where the spec didn't say enough to proceed safely, and were put to the business owner rather than guessed:

**Decision 4 — Internal Transfer's Area dimension (Phase 8).** Phase 7 pooled `EmptyPotInventory`/`PottedPlantStock` as single totals with no physical location, but a "transfer" only means something between two locations. Confirmed: add `AreaId` to both stock tables (nullable, for the pre-Phase-8 "unassigned" pool) before building the transfer mechanism.

**Decision 5 — Booking Reservation architecture (Phase 9).** A dedicated research pass into the existing `dbo.Bookings`/`Data/BookingRepository.cs`/`Pages/Bookings/*` found it entirely wired to the old `dbo.Inventory` (seed-derived raw stock): a booking there writes a header row only, and `FulfillBooking` decrements `Inventory.RemainingQuantity` directly at fulfillment time — no Reserved/Available concept, no relationship to `dbo.PottedPlantStock`. Confirmed: build a **new**, separate `dbo.PottedPlantBookings` reservation system for the new stock chain, leaving the existing Booking module — and its nine existing pages — completely untouched. Two "booking" concepts now exist in the nav (legacy raw-stock Booking under `/Bookings`, new potted-plant reservation under `/Production/PottedPlantBooking`), labeled distinctly to avoid confusion.

**Decision 6 — Purchase Order scope (Phase 11).** No Vendor master existed before this project (`VendorPurchase.VendorName` was free text). Confirmed: Purchase Orders are multi-category (`Fertilizer` / `EmptyPot` / `Other`) with real stock integration on receipt — `Fertilizer` lines insert a new `dbo.FertilizerStock` batch row (exactly how `Pages/Fertilizer/Stock.cshtml.cs` already writes one by hand; that table has no ledger of its own), `EmptyPot` lines post a `'StockIn'` entry to the existing `EmptyPotInventoryTransactions` ledger, `Other` lines are paperwork only.

**Decision 7 — Lab Request scope (Phase 12).** Confirmed as the "full loop": a Lab Request sends a quantity of existing `PottedPlantStock` out to a lab (`'LabSent'`, reduces `PhysicalQuantity`) and later records however much comes back — deliberately independent of what was sent (e.g. 10–15 sent, 30–35 received a few days later, reflecting real multiplication) — via `'LabReceived'` (increases `PhysicalQuantity` by the received amount). Both post against the same pool's existing `PottedPlantStockTransactions` ledger.

**Decision 8 — Role/workflow redesign foundation (Phase 14).** See `claude/plantstockmanager-phase2-redesign-plan.md` for the full audit and plan; this is Migration Plan steps 1-2. Confirmed with the business owner: (a) Kunjir/Kiran/Outlet/Main Office are `dbo.Area` rows distinguished by a new `AreaType` column, not a parallel location table — reuses the `AreaId` link `PottedPlantStock`/`EmptyPotInventory` already carry since Phase 8; (b) Main Office is a central stock/verification location with no Polyhouse of its own, so `Area.PolyhouseId` (tightened to `NOT NULL` in Phase 2) is loosened back to nullable rather than forcing an artificial Polyhouse relationship; (c) a new generic `Roles`/`Permissions`/`RolePermissions`/`UserRoles` model is admin-configurable through `Pages/Admin/Roles` and `Pages/Admin/UserRoles` — `dbo.Designation` (job title) is untouched and not repurposed as the permission system; (d) the previously-empty `Authorization/MinimumAuthorizationLevelRequirement.cs`/`MinimumAuthorizationLevelHandler.cs` stubs are now the real permission-code requirement/handler (see Decision 9 in §9 below for what this changes about their prior "dead code" status). The new potted-plant booking/reservation/dispatch workflow continues to use Phase 9's `dbo.PottedPlantBookings` exclusively; the legacy `dbo.Bookings` module (Decision 5) is untouched and the two remain clearly separated in code and UI, per the business owner's explicit instruction.

**Decision 10 — Cutting Stock as its own ledgered entity, separate from CuttingPlan (Phase 15).** Cuttings never had a location-scoped balance anywhere — `CuttingDeliveries` (Phase 5) is a production-stage record with no `Area` concept. Confirmed: a new `dbo.CuttingStock` (one row per `SpeciesId`+`AreaId`) with its own dedicated ledger `dbo.CuttingStockTransactions`, per Decision 1. "Enter Cutting" is a fresh, independent harvest record with **no** link to `CuttingPlan`/`ActualCutting`/`CuttingDelivery`/`PropagationBatch` — that Phase 3-6 chain is left completely untouched and hidden from the normal menu (not deleted) for whoever still reaches it directly by URL. Cutting-type `InternalTransfers` rows are extended (not replaced) with a confirmation workflow distinct from the immediate-both-sides-write behavior EmptyPot/PottedPlant transfers still use unchanged.

**Decision 11 — Cutting confirmation split into Confirm Receipt / Confirm Transplant, Model B (Phase 16, supersedes part of Phase 15).** After Phase 15 shipped a single-step confirmation (`ConfirmAsync`: confirm receipt and credit the destination in one call), the business owner reviewed the actual destination semantics and corrected it: **the destination Polyhouse is where a cutting is transplanted, not a second raw-cutting storage location**, so it must never receive a `CuttingStock` credit. Approved workflow: `PendingConfirmation → ConfirmedAwaitingTransplant → Transplanted` (`PendingConfirmation → Rejected` unchanged). `ConfirmReceiptAsync` records `ConfirmedQuantity`/discrepancy only — no ledger row, no `PhysicalQuantity` change. `ConfirmTransplantAsync` (opened immediately after Confirm Receipt, no extra navigation) is the **only** point stock moves: one-sided, it decreases the source `CuttingStock.PhysicalQuantity` by `ConfirmedQuantity` and writes exactly one `'Transplanted'` ledger row — nothing is ever credited to the destination. The old `ConfirmAsync` was deleted outright (confirmed via grep: zero callers, since no UI had called it yet). Also added: `CuttingStock.InTransitQuantity` (a maintained balance column, touched only inside `ReserveInTransitAsync`/`ReleaseInTransitAsync`/`RecordTransplantAsync`) and a DB-computed, `PERSISTED` `AvailableQuantity = PhysicalQuantity - InTransitQuantity`, so the same physical cuttings can't be sent twice while an earlier transfer of theirs is still in flight — mirrors the project's existing computed/persisted-column pattern (`CuttingStockTransactions.AfterQuantity`). `CancelAsync`'s Cutting branch was simplified to match: only a `'Transplanted'` transfer can be reversed (single credit back to the source); `PendingConfirmation`/`Rejected`/`ConfirmedAwaitingTransplant` each return an explanatory error instead of attempting a reversal that was never possible for them.

**Decision 12 — Growing Partner as a separate entity from `dbo.Vendors` (Phase 17).** New business information: Area supervision can be handled by external Growing Partners (not only internal employee-supervisors), who may run production and sell directly. Confirmed with the business owner (see `claude/plantstockmanager-vendor-architecture-analysis.md`): the existing `dbo.Vendors` (Phase 11) is procurement-only (fertilizer/empty-pot Purchase Orders) and must **not** be reused or extended for this. A new `dbo.GrowingPartners` master was created instead, linked to `dbo.Area` via a nullable `Area.GrowingPartnerId`. Nullable so every existing Area row is unaffected (NULL = internally run, today's behavior unchanged). Because `PottedPlantStock`/`EmptyPotInventory` (Phase 8) and `CuttingStock` (Phase 15) are already `AreaId`-scoped, Growing-Partner stock separation falls out of this one column with **no new stock tables**. `dbo.UserRoles`/`Roles`/`Permissions`/`RolePermissions` are untouched in this phase — access-control scoping by Growing Partner is deferred to Phase B. Phase 16 (Cutting Model B) is untouched: its repository methods reference only `AreaId`/`SpeciesId`/`CuttingStockId`, never Supervisor/Vendor/ownership.

**Decision 13 — Area-scope enforcement as a new, orthogonal claim/service pair, not a rework of the Permission system (Phase B).** Inspection found the existing Phase 14 Permission-code system (`Roles`/`Permissions`/`RolePermissions`/`UserRoles`, `MinimumAuthorizationLevelHandler`, `PermissionAuthorizationPolicyProvider`) answers "can this user do X at all" and is fully reused as-is; it has never answered "for which Area," and `UserRoles.AreaId` was stored but never read by any authorization path before this phase (only used for display, and — unfiltered by Area — to compute the global Permission-claim set). Confirmed: add two new claim types stamped at login alongside the existing "Permission" claims (`RoleName` per `UserRoles` row; `AreaAccess` per `UserRoles` row that has a non-null `AreaId`), and a new `Authorization/AreaAccessService.cs` that reads them. `UserRoles` itself is unchanged — no redundant `GrowingPartnerId` column, no parallel scope table. `Admin`/`Management`/`MainOfficeOfficer` bypass Area-scoping by design (full administration; cross-location read-only visibility per the approved role table; Main Office is a controlled central operation that must not be restricted like a Growing-Partner-owned Area, per explicit instruction). **Operational note:** Phase 14's Migration Plan step 4 gave every existing user a temporary blanket `Admin` role grant as a safety net — since `Admin` is a full-access role here too, this enforcement has no visible effect for any user until the business owner uses the existing `Pages/Admin/UserRoles` page to replace that temporary grant with each user's real, Area-scoped role, exactly as Phase 14's own documentation already instructed. This is intentional, not a bug: it means Phase B introduces zero behavior change for today's users while making the mechanism fully ready the moment real roles are assigned. Capability flags (Mother Plant/Cutting/Pot/Tray/Sale) were considered and **not** added as a new table: Phase 14 already seeded equivalent permission codes (`MotherPlant.*`, `Kunjir.*`, `Kiran.*`, `Outlet.*`, `MainOffice.*`), which the existing Permission system already represents cleanly — no new schema needed.

**Decision 14 — Main Office → Growing Partner starter material reuses `dbo.InternalTransfers`/`dbo.PottedPlantStock` under a new, distinct `StockType = 'MainOfficeIssue'` (Phase 18 / Phase C).** Inspection of the existing `'PottedPlant'` StockType found it is the immediate, no-confirmation, both-sides-write transfer other Areas already rely on (Phase 8) — reusing it as-is for this new workflow would have silently changed its meaning for everyone else. Confirmed instead: a fourth, additive `StockType` value, `'MainOfficeIssue'`, with its own lifecycle inside `InternalTransferRepository` (`PendingConfirmation → Completed`/`Rejected`, no new Status values needed) and its own `ConfirmMainOfficeIssueAsync` method — sent by Main Office (source forced server-side to a genuine `AreaType = 'MainOffice'` Area), confirmed by the Growing Partner Area (destination forced server-side to an active, `GrowingPartnerId`-linked Area), with a "sent vs received" discrepancy exactly like Cutting's Confirm Receipt, but resolved in **one** step rather than two — there is no separate "Transplant" stage, because (unlike Cutting) the destination is already fixed at creation, not chosen at confirmation time. `PottedPlantStock` gains a new, independently-maintained `InTransitQuantity` column (mirrors `CuttingStock.InTransitQuantity`, Decision 11) so the same physical stock can't be issued twice while a transfer is awaiting confirmation; the existing `AvailableQuantity` computed property/persisted column (`PhysicalQuantity - ReservedQuantity`, relied on by Booking/Dispatch, Phase 9/10) is **not** redefined — "available to issue" (`Physical - Reserved - InTransit`) is computed only inside the new `ReserveInTransitAsync`/`ReleaseInTransitAsync` pair, never as a second persisted column. `RejectAsync`/`CancelAsync` (shared with EmptyPot/PottedPlant/Cutting) each gained one new sibling branch keyed on `StockType == "MainOfficeIssue"`; every existing branch is untouched (confirmed: file-diff review + Phase 16 files' modification timestamps show zero changes since before this phase started). No new permission code was added — inspection found the existing `InternalTransfer.View`/`InternalTransfer.Enter` codes (Phase 14) already represent "enter/confirm internal transfers" accurately; that `KiranSupervisor`/`OutletSupervisor` don't currently hold them is flagged as a business decision for the admin to make via the existing `Pages/Admin/Roles` UI, not something this phase should guess at or silently seed. Dedicated pages under `Pages/Production/MainOfficeIssue/` were built (mirroring Phase 16's own precedent of dedicated Cutting pages) rather than extending the shared `Pages/Production/InternalTransfer/Create.cshtml`/`Edit.cshtml`, keeping the new Area-authorization logic fully isolated from any Phase-16-adjacent shared page code.

**Decision 15 — Cutting Stock → Pot Production as a second, additive source on the existing `dbo.PotProduction` table, not a parallel production table (Phase 19 / Phase D).** Inspection of `Data/PotProductionRepository.cs`/`Database/Phase7_PotProduction.sql` found `PropagationBatchId`/`MotherPlantId` were `NOT NULL`, and two scalar-function-backed `CHECK` constraints (`CK_PotProduction_MatchesPropagationBatch`, `CK_PotProduction_WithinSurvivedQuantity`) rejected any row with a NULL `PropagationBatchId` outright — both had to be relaxed for a Cutting-sourced row to be insertable at all. Confirmed direction, exactly per the recommended model: `PropagationBatchId`/`MotherPlantId` relaxed to nullable; new nullable `SourceCuttingStockId INT NULL` + `FK_PotProduction_CuttingStock` + index; new nullable `CuttingQuantityConsumed DECIMAL(18,2) NULL`. Two new CHECK constraints enforce the source rule as an exact XOR (`CK_PotProduction_SourceType`: exactly one of `PropagationBatchId`/`SourceCuttingStockId`, with `MotherPlantId`'s presence tied to `PropagationBatchId`'s; `CK_PotProduction_CuttingQuantityConsumed`: `CuttingQuantityConsumed` populated iff `SourceCuttingStockId` is, and never less than `Quantity`) — no case was found needing both sources on one row, so "both populated" stays rejected. The two Phase 7 scalar functions were alterated (drop constraint → drop function → recreate function with a leading `IF @PropagationBatchId IS NULL RETURN 1;` bypass → re-add constraint) rather than replaced with new functions, so every existing (Batch-sourced) row is validated by byte-for-byte the same logic as before Phase 19 — the bypass line is the only change, and no existing row can ever hit it. `Quantity`'s existing meaning ("pots consumed = potted plants produced") is reused unchanged for both paths; the alternate `CuttingQuantityConsumed` field holds cuttings consumed for the new path only, and Production Loss (`CuttingQuantityConsumed - Quantity`) is a **derived C# property** (`PotProduction.Loss`), never a third stored column, per the explicit "no redundant quantity columns" instruction. Both paths still consume `dbo.EmptyPotInventory` and produce `dbo.PottedPlantStock` through the exact same mechanism (`GetOrCreateLockedAsync`/`RecordTransactionAsync`) — nothing about Pot Size/Area handling was duplicated. Cutting Stock consumption reuses the Phase 15 `'Potted'` ledger type on `CuttingStockTransactions`, confirmed via its own header comment to have been reserved-but-unused for exactly this purpose since Phase 15. Reversal needed to CREDIT cuttings back on cancellation, a semantic `CuttingStockTransactions` never had before (its existing `'ReversalRemoval'` type is, by the established convention on every other ledger in this app, strictly a negative/removing entry) — confirmed the one narrow, justified widening this phase makes: adding `'ReversalReturn'` to `CK_CuttingStockTx_Type`, reusing the exact name `dbo.EmptyPotInventoryTransactions` already uses (Phase 8) for the identical "credit stock back on reversal" concept, rather than inventing a new name. No widening was needed on `PottedPlantStockTransactions` (`'Production'`/`'ReversalRemoval'` already there) and no new Permission code was needed (`PotProduction.View`/`PotProduction.Enter`, Phase 14, already cover "view/enter pot production records" regardless of source). Built as a dedicated new page, `Pages/Production/PotProduction/CreateFromCutting.cshtml(.cs)`, alongside the untouched legacy `Create.cshtml(.cs)` — mirroring Phase 18/C's own precedent (`MainOfficeIssue` vs generic `InternalTransfer`) of isolating a new source's Area-authorization logic in its own page rather than a single form with a source toggle.

**Decision 18 — Outlet → Customer Sales (Phase G) reuses `PottedPlantBookings`/`Dispatches`/`PottedPlantStock` wholesale; the one genuine gap was Phase 10's full-dispatch-only design, closed by adding a single maintained column and relaxing two constraints.** Inspection of `PottedPlantBookingRepository`/`DispatchRepository`/`PottedPlantStock`/`AreaAccessService` confirmed every piece of stock accounting the spec asks for already existed, unchanged, since Phase 7/9: `PhysicalQuantity`/`ReservedQuantity`/computed `AvailableQuantity` (Phase 7); `RecordReservationAsync`/`RecordTransactionAsync` (Phase 7/9) already enforce, under `UPDLOCK`/`HOLDLOCK`, every rule spec sections 3/7/22 ask for (booking never touches Physical, reservation can't exceed Physical, Physical can't go negative or below Reserved) — **zero changes to either method or to `PottedPlantStock`'s schema**. The dedicated ledger (`PottedPlantStockTransactions`) and its `'Reservation'`/`'ReservationRelease'`/`'Dispatch'` TransactionTypes (Phase 9/10) were also already exactly right — no new ledger table, no new TransactionType. No Customer master exists anywhere in the codebase (confirmed by grep) and none was added — `PottedPlantBookings.CustomerName`/`Address`/`Contact`/`StateId`/`DistrictId` (Phase 9) reused as-is. No new permission code — `Outlet.View`/`.Confirm`/`.Sell`/`Booking.View`/`.Enter`/`Dispatch.View`/`.Enter` (all Phase 14) were already seeded and already granted to `OutletSupervisor`, confirming (again) that Phase 14 anticipated this exact workflow. **The one genuine architectural gap** (spec section 12, partial dispatch): Phase 10 was built full-dispatch-only — `UQ_Dispatches_Booking` forced exactly one `Dispatches` row per Booking, and `fn_Dispatches_MatchesBooking` forced a Dispatch's `Quantity` to equal the Booking's full `Quantity`; `DispatchRepository.InsertAsync` itself silently overwrote whatever `Quantity` was posted with the Booking's full amount. Since Phase G's own spec explicitly requires partial dispatch with a worked example, this was treated as the "genuine, reported architectural conflict" the standing rules allow resolving (unlike Phase 16, which stays untouched): `Database/Phase21_OutletSalesBookingDispatch.sql` drops `UQ_Dispatches_Booking`, relaxes `fn_Dispatches_MatchesBooking`'s Quantity check from strict equality to a coarse `> 0 AND <= Booking.Quantity` bound (the PRECISE "fits within what's remaining right now" check moves into `DispatchRepository.InsertAsync` under the Booking row's own lock, per spec section 22), and adds exactly one new maintained column, `PottedPlantBookings.DispatchedQuantity` (mirroring the established "maintained running-total column" pattern — `CuttingStock.InTransitQuantity`, `PottedPlantStock.InTransitQuantity` — rather than a live `SUM(Dispatches.Quantity)`); `RemainingQuantity` is a derived C# property, never a second stored column, per the "no redundant quantity columns" convention (Decision 15). Booking's `Status` CHECK widened to add `'PartiallyDispatched'` (`Pending → PartiallyDispatched → Dispatched`, or `Pending`/`PartiallyDispatched → Cancelled`) — no other Status value needed, and `Dispatches.Status` (`Completed`/`Cancelled`) is unchanged, since each individual partial dispatch is still simply Completed or Cancelled on its own row. `DispatchRepository.InsertAsync`/`CancelAsync` were both extended to read/update `DispatchedQuantity` and recompute the resulting Status under the same lock, and `PottedPlantBookingRepository.CancelAsync` was widened to release only the *remaining* Reserved amount (`Quantity − DispatchedQuantity`) rather than the full original `Quantity`, so a `PartiallyDispatched` Booking's still-reserved portion can be released — for a plain `Pending` Booking (`DispatchedQuantity == 0`) this is byte-for-byte the same outcome as before Phase 21. **Found-and-fixed, disclosed, in passing**: `PottedPlantStock.SoldDispatchedQuantity` has existed since Phase 7 as a "cumulative, informational running total," displayed on `PottedPlantStock/{Index,Details}`, but was never actually incremented anywhere — a dormant field. Since `DispatchRepository.InsertAsync`/`CancelAsync` were already being touched for partial dispatch, this was fixed at essentially zero marginal risk (it never enters any Available/Reserved/Physical calculation, purely display). **Area authorization** (spec sections 5, 26): a pre-existing gap dating back to Phase 9/10 (built before Growing Partner/Outlet Areas existed) — `PottedPlantBooking`/`Dispatch`'s `Create`/`Index`/`Details`/`Edit` pages had **zero** `AreaAccessService` checks anywhere. Closed with the now-standard pattern: `Create` pages filter their dropdown to accessible Areas AND independently re-fetch the actual referenced row (`PottedPlantStock` for Booking, the target `PottedPlantBooking` for Dispatch) and check `CanAccessArea` against its *real* `AreaId` before mutating (mirroring Phase D's `CreateFromCutting`/Phase F's `GrowingPartnerToOutlet/Create` fix for the identical structural reason: a posted Id can point at a different Area than whatever the dropdown showed); `Index` pages filter their list; `Details`/`Edit` pages check on every verb (`Get`/`Post`/`Cancel`), fetching the record first and checking its own stored `AreaId`, never a posted value. Full-access roles (Admin/Management/`MainOfficeOfficer`) are unaffected, per every prior phase's convention. **Correction (post-review)**: `PottedPlantBookingRepository.InsertAsync` is now repository-enforced to require that a Customer Booking originate from an active Outlet Area — after re-fetching/locking the target `PottedPlantStock` row and deriving its real `AreaId` (never a posted value), the same transaction re-fetches that Area and rejects the booking unless `Area.IsActive = 1 AND Area.AreaType = 'Outlet'`, before any reservation or booking-row mutation occurs. This complements, and does not replace, the page-level `AreaAccessService` checks: `AreaAccessService` answers "which Outlet (if any) may this user reach," while this repository-level check independently answers "is the target stock an Outlet's stock at all" — closing the gap where a full-access user (or a tampered `PottedPlantStockId`) could otherwise book directly against Growing Partner, MainOffice, or other non-Outlet stock. The check mirrors the identical `AreaType`/`IsActive` validation already used in `InternalTransferRepository.InsertAsync` (Phase F) for its Growing-Partner-to-Outlet destination check. No new table, booking table, permission code, or `AreaAccessService` redesign was introduced; stock reservation/ledger accounting, `PhysicalQuantity`, partial dispatch, and dispatch cancellation/reversal are all unchanged. **Outlet stock visibility** (spec section 14): confirmed to already be fully satisfied with zero new code — `PottedPlantStock/{Index,Details}` was already Area-scoped in Phase E and already shows Physical/Reserved/computed-Available per Area; no `OutletStock` page or table was created.

**Decision 17 — Growing Partner → Outlet (Phase F) reuses the `InternalTransfers`/`PottedPlantStock.InTransitQuantity` architecture wholesale; only two CHECK constraints needed widening, and no new table/column/permission was required.** Inspection of `InternalTransfers`/`InternalTransferRepository`/`PottedPlantStock`/`Area`/`AreaAccessService` confirmed the exact same shape as Decision 14's `MainOfficeIssue` (Phase C) applies here, mirrored rather than merged: a new `StockType = 'GrowingPartnerToOutlet'` value, sender = Growing Partner Area (`Area.GrowingPartnerId IS NOT NULL`), destination = Outlet Area (`Area.AreaType = 'Outlet'`, already added by Phase 14), single confirmation step (`PendingConfirmation → Completed`/`Rejected`, deliberately **not** Phase 16's two-stage `ConfirmedAwaitingTransplant → Transplanted`, since Outlet stock is usable immediately on receipt, per spec item 2). Of the five CHECK constraints touching `InternalTransfers`, only `CK_InternalTransfers_StockType` and `CK_InternalTransfers_SourceMatchesStockType` needed widening (new `Database/Phase20_GrowingPartnerToOutlet.sql`, same guarded drop-and-recreate idempotent pattern as every prior widening); `CK_InternalTransfers_DestinationRequired`/`_DifferentAreas`/`_ConfirmedQuantity` already apply generically to any StockType and needed zero change — confirmed by reading their Phase 8/15/18 definitions directly rather than assuming. **Stock accounting** (spec item 4, "do not invent a second availability system"): `PottedPlantStock.InTransitQuantity` (Phase 18/C) is reused exactly as-is, via the already-fully-generic `ReserveInTransitAsync`/`ReleaseInTransitAsync` — zero new column, satisfying the explicit instruction to prefer existing reservation over a new schema column. A new `InternalTransferRepository.ConfirmGrowingPartnerToOutletAsync` was built as its **own** method (mirroring, not merging into, `ConfirmMainOfficeIssueAsync`) — continuing the established convention that a new source/workflow semantic gets a dedicated method, which also makes the Phase C regression trivially verifiable (`ConfirmMainOfficeIssueAsync` itself has zero lines touched). `RejectAsync`/`CancelAsync`'s existing `MainOfficeIssue` branches were widened with an additive `|| stockType == "GrowingPartnerToOutlet"` condition rather than duplicated, since their InTransit-release/reversal logic is genuinely identical for both StockTypes; three `CancelAsync` error-message **strings** inside that shared branch were generalized from "Main Office Issue"-specific wording to generic "transfer" wording as part of this widening (a disclosed, non-stock-affecting text change — see the Phase F report's Phase C regression section). **Short receipt / discrepancy** (spec items 3, 15): `ConfirmedQuantity`/`DiscrepancyReason` (Phase 15 columns, already generic) hold the confirmed amount and required reason exactly as `MainOfficeIssue` already does; the un-received difference is released from `InTransitQuantity` but never decremented from source `PhysicalQuantity` — reproducing the spec's own worked example (1,000 stock, 500 sent, 480 confirmed → source becomes 520, not 500). Discrepancy reason is a free-text field, **not** a hardcoded dropdown, per spec item 15's explicit "do not hard-code the reason list unless the existing architecture already has one" (none does). **Area authorization** (spec items 9-12): two genuine, newly-identified tampering gaps were found and fixed, neither of them satisfied by simply reusing MainOfficeIssue's pattern verbatim, because MainOfficeIssue's sender (MainOfficeOfficer) is a full-access role by design and never exercised this path before: (1) `GrowingPartnerToOutlet/Create.cshtml.cs`'s `OnPostSendAsync` re-fetches the actual `PottedPlantStock` row server-side and checks `CanAccessArea` against **its own** `AreaId`, not just the posted `areaId` used for the dropdown filter — closing the vector where a legitimate own-Area `areaId` is posted alongside a `pottedPlantStockId` belonging to a *different* Area (this mirrors the identical fix Phase D's `CreateFromCutting.cshtml.cs` needed for the same structural reason); (2) `Pages/Production/InternalTransfer/Edit.cshtml.cs` had **zero** Area check since Phase 8, for any StockType — meaning any authenticated user could view/edit/cancel any transfer via this one generic shared page regardless of the new GrowingPartnerToOutlet-specific authorization built elsewhere; fixed by adding `AreaAccessService` and a `CanAccessTransfer(t) => CanAccessArea(t.SourceAreaId) || CanAccessArea(t.DestinationAreaId)` helper to `OnGetAsync`/`OnPostAsync`/`OnPostCancelAsync`. Sender/receiver separation (spec item 12, Test 7 — a Growing Partner Supervisor cannot confirm their own outgoing transfer) falls out for free from the same `CanAccessArea(User, Transfer.DestinationAreaId)` check `MainOfficeIssue/ConfirmReceipt` already uses: a Growing Partner's own `AreaAccess` claim covers their sending Area, never the Outlet's `DestinationAreaId`. **Permissions**: no new code added — `Outlet.View`/`Outlet.Confirm`/`Outlet.Sell` were already seeded and already granted to `OutletSupervisor` back in Phase 14, anticipating exactly this workflow; `InternalTransfer.Enter` conceptually covers the Growing Partner's send action, consistent with how MainOfficeIssue's send action needed no distinct code either — as with every prior phase, no page yet enforces these via `[Authorize(Policy=...)]`, only `AuthorizeFolder("/Production")` + `AreaAccessService`, consistent with the whole codebase's current state.

**Decision 22 — Ready Confirmation (Phase K / 25) is a new, dedicated Ready Stock domain, scoped one-row-per-Seed-Sowing for traceability, built as an explicit user action with no new `SeedSowings.Status` value.** Inspection first confirmed (grep across `Database/*.sql`/`Models/*.cs`/`Data/*.cs` for `CREATE TABLE.*Ready|dbo\.ReadyStock|dbo\.ReadyConfirmation`) that no Ready Stock/Ready Confirmation table, model, or repository exists anywhere — the only pre-existing "Ready" artifact is the legacy, untouched `Pages/Data/ReadyStock.cshtml(.cs)` report (a different pipeline, against `dbo.Inventory`, already out of scope per Phase J's own inspection) — so this phase designs a wholly new domain rather than extending an existing one. **Closest precedent, deliberately mirrored**: Phase 21/Phase G's `dbo.PottedPlantBookings.DispatchedQuantity` + `dbo.Dispatches` pattern — a parent record tracking a running "how much of me has been fulfilled" total, fulfilled by one or more CHILD event rows (partial fulfillment allowed since `UQ_Dispatches_Booking` was dropped), each validated against the parent's own remaining quantity under the parent row's own lock, with `DispatchRepository.CancelAsync` locking both rows to reverse safely — structurally identical to the spec's own worked examples (500 sown, 300 then 200 confirmed = fully confirmed **allowed**; 300 then 300 = **rejected**, only 200 remains), so it is reused rather than inventing a one-confirmation-per-batch model. **Schema** (`Database/Phase25_ReadyConfirmation.sql`): (1) `dbo.SeedSowings.ConfirmedReadyQuantity` (additive column, `CHECK (>= 0 AND <= QuantitySown)`) — the running total, mirroring `PottedPlantBookings.DispatchedQuantity` exactly, updated only by `ReadyConfirmationRepository.ConfirmAsync`/`CancelAsync` under a lock taken directly against `dbo.SeedSowings` (mirrors `DispatchRepository` writing directly to `PottedPlantBookings.DispatchedQuantity` rather than routing through a separate Booking-repository method) — **deliberately no new `Status` value** (`CK_SeedSowings_Status` stays `'Sown'`/`'Cancelled'` only): a genuine, deliberate divergence from Phase 21/G's own `'PartiallyDispatched'` status precedent, made because nothing else in this app branches on a Sowing-readiness state the way a Booking's Status feeds real downstream decisions elsewhere, so `ConfirmedReadyQuantity` vs `QuantitySown` alone is sufficient and a new status would be unused plumbing — per the spec's own "prefer a confirmed-quantity column over inventing statuses when the existing design already supports it" instruction. (2) `dbo.ReadyStock` (new table) — the confirmed-ready stock POOL, grain **one row per `SeedSowingId` (UNIQUE)**, deliberately NOT pooled across Sowings by Species+Area+Lot the way `dbo.SeedStock`/`dbo.PottedPlantStock`/`dbo.CuttingStock` are: the spec's own explicit traceability rule ("must retain traceability back to the originating Seed Sowing... do not lose original batch identity") would be violated by pooling multiple Sowings' confirmed quantity into one Species+Area row, so the SeedSowing-scoped grain is used instead, with `BatchNo`/`CavityType`/`SowingDate`/`AreaId`/`SpeciesId` denormalized directly from the owning Sowing. Created only the FIRST time a Sowing is actually Ready-Confirmed (`ReadyStockRepository.GetOrCreateLockedAsync`) — never eagerly at Sowing time, per the explicit "no automatic Ready Stock creation" rule. (3) `dbo.ReadyStockTransactions` (new table) — the dedicated ledger for `dbo.ReadyStock`, per Decision 1 (same shape as `SeedStockTransactions`/`PottedPlantStockTransactions`, including the persisted-computed `AfterQuantity` column and the never-negative-after `CHECK`). `TransactionType` is `'Confirmed'` (positive) or `'ReversalRemoval'` (negative) — per Decision 15's naming convention, `'ReversalReturn'` is reserved for crediting a SOURCE pool back; there is none here, only an addition being undone, so `'ReversalRemoval'` is reused rather than a new name. (4) `dbo.ReadyConfirmations` (new table) — the auditable confirmation EVENT/header, one row per explicit "this batch is physically ready" action; plays the exact role `dbo.Dispatches` plays against `dbo.PottedPlantBookings`: it both drives `dbo.ReadyStock`'s ledger and maintains `SeedSowings.ConfirmedReadyQuantity`. Its own `Status` (`'Confirmed'`/`'Cancelled'`) is independent of `SeedSowings.Status`, exactly like `Dispatch.Status` is independent of `PottedPlantBookings.Status`. **Cancellation is supported** (every other production-style table in this app — SeedSowing, PotProduction, Dispatch — already offers one, directly reusable): `ReadyConfirmationRepository.CancelAsync` locks both this row and the parent Sowing row, reverses via a `'ReversalRemoval'` ledger entry, decrements `ConfirmedReadyQuantity`, and marks the row `'Cancelled'` — never deletes it, and never deletes the underlying `ReadyStock` pool row either (only its `Quantity` moves). Batch code uses the existing `dbo.BatchNumberSequences` mechanism with prefix `"RDY"` (confirmed unused by grep across every existing `GetNextBatchNumberAsync(conn, tx, "...")` call site: `AC, BK, CD, CUT, DIS, LAB, LBR, MP, PO, POT, PROP, SI, SOW, TR` are already in use) — no `MAX()+1` anywhere. **Transaction safety**: `ReadyConfirmationRepository.ConfirmAsync` runs the full 8-step sequence in one `SqlTransaction` — lock/re-fetch the Sowing (`WITH (UPDLOCK, HOLDLOCK)`) → reject if `Status <> 'Sown'` → reject if the requested quantity exceeds `QuantitySown - ConfirmedReadyQuantity` (checked under this same lock, so a concurrent confirmation against the same Sowing cannot race it) → get-or-create the `ReadyStock` row → insert the `ReadyConfirmations` header (so its Id is available as `ReferenceId`) → write the `ReadyStockTransactions` ledger entry (`+quantity`) → update `SeedSowings.ConfirmedReadyQuantity` → commit; any failure rolls back the whole transaction, so no partial stock movement is ever possible. **Area authorization**: never inside the repository — `Pages/Production/ReadyConfirmation/Confirm.cshtml.cs` re-fetches the Sowing via `SeedSowingRepository.GetByIdAsync` on both GET and POST and checks `AreaAccessService.CanAccessArea` against its real, freshly-read `AreaId` before ever calling `ConfirmAsync`, exactly mirroring `SeedSowing/Edit.cshtml.cs`'s own split between page-level Area authorization and repository-level stock integrity; the Confirm form posts no `AreaId` field at all, so there is nothing to tamper with. No new permission code — `Pages/Production/ReadyConfirmation/*` lives under the existing `AuthorizeFolder("/Production")` policy, exactly like every other Production page. **Ready Alerts integration**: `SeedSowingRepository.GetAlertCandidatesAsync`'s `WHERE` clause gained one additional `AND sw.ConfirmedReadyQuantity < sw.QuantitySown` — `ClassifyReadyAlert` itself is completely untouched, per the explicit "do not change the Phase J classification rules unnecessarily" instruction; a fully-confirmed Sowing now drops out of Ready Alerts entirely, while a partially-confirmed one continues to alert for its genuine remaining quantity, exactly as the spec requires. The new `SeedSowingRepository.GetReadyForConfirmationAsync()` (the Ready Confirmation page's own eligible-batches source) is deliberately **not** restricted to only currently-alerted Sowings — any active (`'Sown'`) Sowing with remaining quantity is eligible, since Ready Alerts are a helpful nudge, not a gate (Phase J's own "Ready Alerts... remain alerts only"), and the spec's workflow diagram has the Supervisor physically verify the crop, which may happen before the Expected Ready Date. **UI**: `Pages/Production/ReadyConfirmation/Index.cshtml(.cs)` (eligible-batches list, Area-scoped via `AreaAccessService`, showing each batch's alert category for context), `Confirm.cshtml(.cs)` (read-only Sowing info incl. immutable `ExpectedReadyDate`/`ReadyStockDays` + the Ready Quantity input — no automatic action of any kind, regardless of how overdue the batch is), `History.cshtml(.cs)` (per-Sowing confirmation result/history, including the Cancel action). ## 2. Traceability chain

```
Mother Plant → Cutting Plan → Actual Cutting → Cutting Delivery → Propagation Batch
  → Pot Production → Potted Plant Stock → Booking/Reservation → Dispatch
```

Every stage's table carries denormalized copies of its parent's key identifying fields (e.g. `ActualCuttings.MotherPlantId`/`SpeciesId` copied from `CuttingPlans`), always derived server-side from the locked parent row and never trusted from the caller, backstopped by a scalar-function `CHECK` constraint (`fn_..._MatchesParent`) at the database level. A dispatched plant is traceable backward by opening each stage's own Details page in turn: Dispatch → Booking → Potted Plant Stock → Pot Production → Propagation Batch → Cutting Delivery → Actual Cutting → Cutting Plan → Mother Plant. `Pages/Production/Dashboard/Index` gives the fleet-level summary across all stages; it reads every module's own repository and stores nothing itself.

Lab Request and Labour Log sit outside this linear chain: a Lab Request references one `PottedPlantStock` pool directly (send/receive against the same pool), and a Labour Log optionally references any other record via a loose `ReferenceType`/`ReferenceId`/`ReferenceCode` (no hard FK, matching how the stock ledgers themselves treat references) rather than participating in the stock chain itself.

As of Phase 19/D, `Pot Production` has a second, parallel entry point that rejoins the same chain from `Potted Plant Stock` onward:

```
Growing Partner → Area → Cutting Stock → Pot Production → Potted Plant Stock → Booking/Reservation → Dispatch
```

A `PotProduction` row is traceable back to exactly one of the two sources (`PropagationBatchId` XOR `SourceCuttingStockId`, never both, never neither — `CK_PotProduction_SourceType`), and from `Potted Plant Stock` onward every existing downstream stage (Booking, Dispatch, Lab Request) treats stock from either source identically, since neither carries a source-specific column.

## 3. Stock rules (enforced, not just documented)

- **Never negative stock** — every `RecordTransactionAsync`/`RecordReservationAsync` locks the row (`UPDLOCK, HOLDLOCK`), computes `after = before + delta`, and rejects the operation (returns `(false, message)`, no partial write) if `after < 0`.
- **Never exceed Available** — Booking/Lab-Send validate `after >= Reserved` (can't reduce Physical below what's already reserved) or `after <= Physical` (can't reserve more than Physical), depending on which side is moving.
- **Physical / Reserved / Available** — `PottedPlantStock.AvailableQuantity` is a C# computed property (`PhysicalQuantity - ReservedQuantity`), mirrored by a persisted computed column in SQL. Booking/Lab-Request-Send only ever change `ReservedQuantity` or `PhysicalQuantity` respectively, matching the rule "Booking reserves but never physically reduces stock; Dispatch completion reduces physical stock."
- **Every stock movement creates a ledger row** — confirmed by direct grep across every repository: the only three `UPDATE ... SET PhysicalQuantity`/`SET ReservedQuantity` statements in the entire codebase are the ones inside `RecordTransactionAsync`/`RecordReservationAsync` themselves, each immediately followed by the matching `INSERT` into that entity's ledger, in the same transaction.
- **Multi-step operations use transactions** — every `InsertAsync`/`CancelAsync`/`InsertReceiptAsync`/`RecordResultAsync` that touches more than one table opens its own `SqlTransaction` and commits or rolls back as a unit.

## 4. Batch numbering

One reusable mechanism, `Data/BatchNumberRepository.GetNextBatchNumberAsync(conn, tx, prefix, year, padding=5)`, backed by `dbo.BatchNumberSequences` (`MERGE ... WITH (HOLDLOCK)`, concurrency-safe, no `MAX()+1` anywhere in the codebase — confirmed by grep). Prefixes in use: `MP, CUT, AC, CD, PROP, POT, TR, BK, DIS, PO` (the originally approved list) plus `LAB` (Lab Request) and `LBR` (Labour Log) — two phases the original prefix list didn't reach, extended with the same generic mechanism rather than inventing a second numbering scheme.
